Khi ứng dụng Java ORM chạy chậm trong môi trường Production, một nguyên nhân phổ biến cần kiểm tra là **việc lấy dữ liệu không tối ưu (Inefficient Fetching)**.

Trong đó, **N+1 Query Problem** là một lỗi hiệu năng phổ biến, có thể khiến số lượng truy vấn Database tăng mạnh và làm chậm ứng dụng.

---
## 1. Bản chất: EAGER vs LAZY Fetching

Mỗi quan hệ trong JPA (`@ManyToOne`, `@OneToMany`,...) đều có cấu hình `fetch`:

```java
@ManyToOne(fetch = FetchType.LAZY)
private Department department;

@OneToMany(mappedBy = "department", fetch = FetchType.LAZY)
private List<Employee> employees = new ArrayList<>();
```

### `LAZY`

Chỉ tải entity liên quan **khi thực sự cần sử dụng**.

### `EAGER`

Yêu cầu entity liên quan được **nạp ngay**, trước khi entity chính được trả về cho application.

> ⚠️ **Hiểu lầm kinh điển: `EAGER` = `JOIN`**

`FetchType.EAGER` **không có nghĩa Hibernate luôn dùng SQL `JOIN`**.

Ví dụ:

```java
List<Employee> employees =
    entityManager.createQuery(
        "SELECT e FROM Employee e",
        Employee.class
    ).getResultList();
```

Nếu `department` là `EAGER`, Hibernate có thể phải thực hiện thêm các truy vấn để nạp `Department`. Trong một số trường hợp, điều này có thể dẫn đến **N+1 Query**.

Vì vậy:

> **EAGER không phải là cách giải quyết N+1.**

## 2. Vấn đề N+1 Query là gì?

Giả sử bạn cần hiển thị danh sách **100 nhân viên** kèm tên phòng ban của họ:

```java
List<Employee> employees = entityManager
    .createQuery("SELECT e FROM Employee e", Employee.class)
    .getResultList(); // Query 1: Lấy danh sách 100 nhân viên

for (Employee e : employees) {
    // Truy cập association có thể kích hoạt thêm SELECT
    System.out.println(
        e.getName() + " - " + e.getDepartment().getName()
    );
}
```

Nếu `department` được fetch riêng cho từng `Employee` và 100 nhân viên thuộc **100 Department khác nhau**, có thể phát sinh:

```text
[Query 1]
SELECT * FROM employee;
-- Trả về 100 employees

[Query 2]
SELECT * FROM department WHERE id = 1;
-- Department của employee 1

[Query 3]
SELECT * FROM department WHERE id = 2;
-- Department của employee 2

...

[Query 101]
SELECT * FROM department WHERE id = 100;
-- Department của employee 100
```

**Tổng cộng:**

```text
1 query lấy Employee
+
100 query lấy Department
=
101 queries
```

Đây chính là **N+1 Query Problem**:

> **1 query** để lấy danh sách entity chính + **N query** để lấy dữ liệu liên quan cho từng entity.

### ⚠️ Lưu ý

N+1 **không phải lúc nào cũng đúng bằng `1 + N` query**. Số query thực tế còn phụ thuộc vào:

* Fetch strategy (`LAZY` / `EAGER`)
* Các association được truy cập
* Persistence Context
* Hibernate caching
* Cách Hibernate thực hiện fetching

Điểm quan trọng là: **khi mỗi entity trong danh sách kích hoạt thêm một query riêng để lấy association, số lượng query có thể tăng theo số lượng entity.**

## 3. Các giải pháp xử lý N+1 Query
<Tabs items={['1. JOIN FETCH (HQL/JPQL)', '2. JPA EntityGraph', '3. @BatchSize', '4. DTO Projection']}>

<Tab value="1. JOIN FETCH (HQL/JPQL)">

`JOIN FETCH` cho phép Hibernate **fetch association ngay trong cùng truy vấn JPQL/HQL**, thường giúp tránh các truy vấn phụ do lazy loading.

```java
String hql = """
    SELECT e
    FROM Employee e
    JOIN FETCH e.department
    """;

List<Employee> employees = entityManager
    .createQuery(hql, Employee.class)
    .getResultList();
```

Hibernate có thể sinh SQL tương tự:

```sql
SELECT
    e.id,
    e.name,
    e.department_id,
    d.id,
    d.name
FROM employee e
INNER JOIN department d
    ON e.department_id = d.id;
```

Thay vì:

```text
1 query Employee
+
N query Department
```

ta có thể chỉ cần:

```text
1 query Employee + Department
```

→ Với use case phù hợp, `JOIN FETCH` là một cách trực tiếp để giải quyết N+1.

<Callout type="error" title="Cảnh báo MultipleBagFetchException">

Hibernate có thể gặp `MultipleBagFetchException` khi cố gắng `JOIN FETCH` **nhiều collection kiểu bag** (`List` không có thứ tự/index được Hibernate quản lý như bag) trong cùng một query.

Ví dụ:

```java
SELECT d
FROM Department d
JOIN FETCH d.employees
JOIN FETCH d.projects
```

Nếu cả `employees` và `projects` đều là bag, việc join đồng thời có thể tạo ra **Cartesian Product / row multiplication**, khiến số dòng kết quả tăng mạnh.

Vì vậy không nên tùy tiện `JOIN FETCH` nhiều collection trong cùng một query.

</Callout>

</Tab>

<Tab value="2. JPA EntityGraph">

`EntityGraph` cho phép định nghĩa **fetch plan** cho một use case mà không cần thay đổi câu JPQL/HQL.

```java
@Entity
@NamedEntityGraph(
    name = "Employee.withDepartmentAndProjects",
    attributeNodes = {
        @NamedAttributeNode("department"),
        @NamedAttributeNode("projects")
    }
)
public class Employee {
    // ...
}
```

Sử dụng:

```java
EntityGraph<?> graph =
    entityManager.getEntityGraph(
        "Employee.withDepartmentAndProjects"
    );

List<Employee> list = entityManager
    .createQuery(
        "SELECT e FROM Employee e",
        Employee.class
    )
    .setHint("jakarta.persistence.fetchgraph", graph)
    .getResultList();
```

### `fetchgraph`

Các attribute được chỉ định trong graph được yêu cầu fetch; các attribute khác được xem là `LAZY` theo semantics của JPA fetch graph.

### `loadgraph`

Các attribute được chỉ định trong graph được yêu cầu fetch; các attribute khác giữ fetch strategy theo mapping.

→ `EntityGraph` phù hợp khi muốn **thay đổi fetch plan theo từng use case** mà không phải viết lại query.

</Tab>

<Tab value="3. @BatchSize">

`@BatchSize` không loại bỏ hoàn toàn việc fetch association, mà giúp Hibernate **gom nhiều entity/collection cần lazy loading vào các batch**, giảm số lượng SQL query.

Ví dụ:

```java
@Entity
public class Department {

    @Id
    private Long id;

    @BatchSize(size = 20)
    @OneToMany(mappedBy = "department")
    private List<Employee> employees;
}
```

Khi Hibernate cần lazy load employees của nhiều Department, thay vì:

```sql
SELECT * FROM employee WHERE department_id = 1;
SELECT * FROM employee WHERE department_id = 2;
SELECT * FROM employee WHERE department_id = 3;
...
```

Hibernate có thể gom chúng thành các batch:

```sql
SELECT *
FROM employee
WHERE department_id IN (1, 2, 3, ..., 20);
```

Ví dụ có 100 Department cần load collection:

```text
100 query riêng lẻ

        ↓

@BatchSize(size = 20)

        ↓

khoảng 5 batch query
```

→ `@BatchSize` **giảm số lượng query**, nhưng không nhất thiết biến N+1 thành đúng 1 query.

</Tab>

<Tab value="4. DTO Projection">

Nếu use case chỉ cần một số dữ liệu để hiển thị hoặc trả về API, có thể dùng **DTO Projection** thay vì load toàn bộ entity.

```java
public record EmployeeSummaryDTO(
    Long id,
    String name,
    String departmentName
) {}
```

Query trực tiếp vào DTO:

```java
List<EmployeeSummaryDTO> result = entityManager
    .createQuery("""
        SELECT new com.example.dto.EmployeeSummaryDTO(
            e.id,
            e.name,
            d.name
        )
        FROM Employee e
        JOIN e.department d
        """, EmployeeSummaryDTO.class)
    .getResultList();
```

### Ưu điểm

* Chỉ lấy những cột thực sự cần thiết.
* Không trả về entity nên phù hợp với các use case chỉ đọc dữ liệu.
* Giảm overhead liên quan đến entity management.
* Phù hợp cho **API response, report và màn hình danh sách**.

> ⚠️ DTO Projection không mặc định là **“nhanh nhất”** trong mọi trường hợp. Hiệu năng còn phụ thuộc vào SQL, index, số lượng dữ liệu, execution plan và workload.

</Tab>

</Tabs>

## 4. HQL Querying
HQL (Hibernate Query Language) là ngôn ngữ truy vấn của Hibernate, cho phép truy vấn Entity và thuộc tính của Entity thay vì truy vấn trực tiếp Table và Column như SQL.

```java
// 1. Projection – chọn một số trường cần thiết
List<Object[]> rows = entityManager.createQuery(
    "SELECT e.name, e.salary " +
    "FROM Employee e " +
    "WHERE e.salary > :minSalary",
    Object[].class
)
.setParameter("minSalary", 50000.0)
.getResultList();

// 2. Aggregation + GROUP BY + HAVING
List<Object[]> deptStats = entityManager.createQuery(
    "SELECT e.department.name, COUNT(e), AVG(e.salary) " +
    "FROM Employee e " +
    "GROUP BY e.department.name " +
    "HAVING COUNT(e) >= 5 " +
    "ORDER BY AVG(e.salary) DESC",
    Object[].class
)
.getResultList();

// 3. Subquery
List<Employee> highEarners = entityManager.createQuery(
    "SELECT e " +
    "FROM Employee e " +
    "WHERE e.salary > (" +
    "    SELECT AVG(emp.salary) " +
    "    FROM Employee emp" +
    ")",
    Employee.class
)
.getResultList();
```

### 1. Projection

Chỉ lấy những field cần thiết thay vì load toàn bộ `Employee`:

```text
Employee
   ↓
SELECT name, salary
   ↓
Object[]
```

Ví dụ:

```java
SELECT e.name, e.salary
FROM Employee e
```

Kết quả mỗi dòng có thể được biểu diễn dưới dạng:

```text
["Nguyen Van A", 50000]
["Tran Van B", 60000]
```

### 2. Aggregation + GROUP BY + HAVING

Dùng các hàm tổng hợp như:

```text
COUNT()
AVG()
SUM()
MIN()
MAX()
```

Ví dụ:

```java
SELECT e.department.name,
       COUNT(e),
       AVG(e.salary)
FROM Employee e
GROUP BY e.department.name
HAVING COUNT(e) >= 5
ORDER BY AVG(e.salary) DESC
```

→ Thống kê số nhân viên và mức lương trung bình theo từng phòng ban.

### 3. Subquery

Subquery là một query nằm bên trong một query khác.

Ví dụ:

```java
WHERE e.salary > (
    SELECT AVG(emp.salary)
    FROM Employee emp
)
```

→ Lấy những nhân viên có mức lương **cao hơn mức lương trung bình của toàn bộ nhân viên**.

> **Cách nhớ:**
> `SELECT` → chọn dữ liệu
> `GROUP BY` → gom nhóm
> `HAVING` → lọc sau khi gom nhóm
> `ORDER BY` → sắp xếp
> `Subquery` → query nằm bên trong query khác

## 5. Chiến lược tối ưu tổng thể (Cheatsheet)

```text
                         Cần đọc dữ liệu từ DB
                                  │
                  ┌───────────────┴───────────────┐
                  ▼                               ▼
          Chỉ cần HIỂN THỊ                 Cần UPDATE sau khi đọc
       (Read-Only / API / Report)              (Business Logic)
                  │                               │
                  ▼                               ▼
          DTO Projection                   FetchType.LAZY
       (SELECT new MyDTO(...))                    │
                                                  ▼
                                    Cần nạp quan hệ liên quan?
                                                  │
                               ┌──────────────────┴──────────────────┐
                               ▼                                     ▼
                        Quan hệ cần fetch                  Nhiều entity cần
                         ngay trong query?                lazy loading?
                               │                                     │
                               ▼                                     ▼
                         JOIN FETCH                           @BatchSize
                               │
                               │
                               └──────────────┐
                                              ▼
                                        EntityGraph
```

### Nguyên tắc lựa chọn

| Use Case                                  | Giải pháp phù hợp  |
| ----------------------------------------- | ------------------ |
| Read-Only / API / Report                  | **DTO Projection** |
| Cần entity để xử lý Business Logic        | **Entity + LAZY**  |
| Biết rõ association cần fetch trong query | **JOIN FETCH**     |
| Muốn thay đổi fetch plan theo use case    | **EntityGraph**    |
| Có nhiều lazy association cần load        | **@BatchSize**     |
